# Alveo V80 deployment report

[← Deployment index](README.md)

## Part

| Field | Value |
|---|---|
| Part name | `xcv80-lsva4737-2MHP-e-S` |
| Family | Versal Premium |
| Speed grade | `-2MHP-e` |
| Silicon | **Engineering Sample** (the `-S` suffix; only V80 part shipped with Vivado 2025.2) |
| SLRs | 2 |
| Clock uncertainty | **~0.300 ns** (ES characterisation conservatism; expected ~0.05 ns on production silicon) |

The `-S` clock-uncertainty penalty alone costs ~0.265 ns of post-route
WNS vs an equivalent production UltraScale+ part. This is the dominant
factor in why V80 ES misses 250 MHz on configurations that U250 and
U55C close comfortably.

## Capacity

| Resource | Total | Per-cache @ 512 KB / 8w / SDP+URAM | Per-cache @ 1 MB / 8w / SDP+URAM | Per-cache @ 2 MB |
|---|---:|---:|---:|---:|
| CLB LUTs   | 2 574 208 | 1516–1666 | 1634 | 1769 |
| CLB FFs    | 5 148 416 |  802–886  |  840 |  900 |
| BRAM tiles |   3 741   |    5      |    2 |    4 |
| URAM       |   1 925   |   16      |   34 |   66 |

V80 has the largest LUT and BRAM budgets of the three target boards;
URAM is in the same league as U55C (1925 vs 1936).

## Validated post-route results

8-way / SDP+URAM / GRASP / `INCLUDE_VICTIM=0` / `DATABANK_SDP=1`.

### 512 KB

| Target MHz | Knobs | WNS (ns) | Achievable MHz | Status |
|---|---|---:|---:|---|
| 200 (5.0 ns)   | baseline                                 | +0.062 | 203 | ✓ MET (recommended for ES silicon if you only need 200) |
| **250 (4.0 ns)**   | **tuned (DBL=3, WIR=1, CD=1, aggressive directives)** | **+0.012** | **~250** | **✓ MET on ES (with CD=1)** |
| 250 (4.0 ns)   | tuned + production-silicon projection (`CLOCK_UNCERTAINTY_NS=0.035`) | +0.030 | ~252 | ✓ MET projected for production |
| 286 (3.5 ns)   | tuned                                     | -0.378 | ~258 | ES caps near 258 MHz |
| 300 (3.333 ns) | tuned                                     | -0.524 | ~259 | ES clock-uncertainty bound |

### 1 MB / 2 MB (post-route on ES silicon)

| Cache | Target MHz | Knobs | WNS (ns) | Achievable MHz |
|---|---:|---|---:|---:|
| **1 MB** | **250 (4.0 ns)** | **tuned (CD=1)** | **-0.004** | **~250 (essentially MET on ES; one route reseed closes)** |
| 1 MB | 300 (3.333 ns) | tuned (CD=1) | -0.849 | ~239 |
| 1 MB | 350 (2.857 ns) | tuned (CD=1) | -1.584 | ~225 |
| 2 MB | 250 (4.0 ns)   | tuned (CD=1) | -0.380 | ~228 |
| 2 MB | 250 (4.0 ns)   | tuned (CD=1) + production-silicon projection | -0.345 | ~230 (only +2 MHz over ES — confirms 2 MB is structurally bound by the 66-URAM cascade, not clock uncertainty) |
| 2 MB | 300 (3.333 ns) | tuned (CD=1) | -1.350 | ~214 |
| 2 MB | 350 (2.857 ns) | tuned (CD=1) | -1.931 | ~209 |

**Diminishing returns**: at 2 MB pushing the target from 300 to 350
MHz makes the result strictly WORSE (209 vs 214 MHz). The 66-URAM
cascade is a structural binding path; aggressive synth just spreads
logic further chasing the impossible target.

## Multi-CU deployment arithmetic

| Configuration             | URAM | %URAM | BRAM | %BRAM |
|---|---:|---:|---:|---:|
| 16 CU × 512 KB / 8w / SDP | 256  | 13 %  |  80  |  2 %  |
| 32 CU × 512 KB            | 512  | 27 %  | 160  |  4 %  |
| 16 CU × 1 MB              | 544  | 28 %  |  32  |  1 %  |
| 32 CU × 1 MB              | 1088 | 57 %  |  64  |  2 %  |
| 16 CU × 2 MB              | 1056 | 55 %  |  32  |  1 %  |

V80 has the best resource-headroom story for very dense multi-CU
deployments: 32 CU × 1 MB or 16 CU × 2 MB both leave ~45 % URAM
budget. **But timing on ES silicon caps deployment at ~200 MHz on
512 KB and ~210 MHz on 1 MB / 2 MB.**

## When to pick V80

| Scenario | V80 fit |
|---|---|
| Versal-only target (NoC integration, AIE-ML) | V80 is mandatory |
| Highest CU count / largest aggregate L2 | V80 has the room |
| 200 MHz deployment today | V80 ES is fine |
| 250+ MHz deployment today | use U250 or U55C (production silicon) until V80 production ships |

## Recommended configuration for ES silicon (200 MHz target)

```sv
l2_cache #(
    .POLICY              (GRASP),
    .LINES               (1024),
    .LINE_W              (16),
    .WAYS                (8),
    .BLOCK_W             (32),
    .DB_LATENCY          (2),        // 200 MHz target, baseline pipeline depth
    .INCLUDE_VICTIM      (0),
    .DATABANK_SDP        (1),
    .SDP_WRITE_INPUT_REG (0),        // not needed at 200 MHz
    .CASCADE_DEPTH       (1)         // V80 URAM288E5: CD=1 is strictly better than CD=8
    // ADDR_RANGE_L / ADDR_RANGE_H per system map
) u_cache ( /* AXI */ );
```

`./syn/vivado/v80_synth.sh` defaults `CASCADE_DEPTH=1` already.

## Recommended configuration for production silicon (when it ships, 250 MHz)

```sv
l2_cache #(
    .POLICY              (GRASP),
    .LINES               (1024),
    .LINE_W              (16),
    .WAYS                (8),
    .BLOCK_W             (32),
    .DB_LATENCY          (3),        // tuned for higher frequency
    .INCLUDE_VICTIM      (0),
    .DATABANK_SDP        (1),
    .SDP_WRITE_INPUT_REG (1),
    .CASCADE_DEPTH       (1)         // V80 URAM288E5: keep CD=1
    // ADDR_RANGE_L / ADDR_RANGE_H per system map
) u_cache ( /* AXI */ );
```

## CASCADE_DEPTH impact on V80 (post-route, tuned knobs)

`CASCADE_DEPTH=1` is a strict improvement on V80 across all measured
sizes (Versal `URAM288E5` primitive has different cascade timing than
UltraScale+ `URAM288`). `v80_synth.sh` defaults to `CASCADE_DEPTH=1`.

| Cache | Target MHz | CD=8 (baseline) | **CD=1** (default) | Δ |
|---|---:|---:|---:|---:|
| 512 KB | 250 | -0.090 ns (~244 MHz) | **+0.012 ns (~250 MHz, ✓ MET)** | +0.102 ns |
| 1 MB   | 250 | (not measured pre-CD=1) | **-0.004 ns (~250 MHz, essentially MET)** | huge — 1 MB previously stuck near 213 MHz at 300 MHz target |
| 1 MB   | 300 | -1.370 ns (~213 MHz) | -0.849 ns (~239 MHz) | +0.521 ns |
| 2 MB   | 250 | (not measured pre-CD=1) | -0.380 ns (~228 MHz) | structurally bound |
| 2 MB   | 300 | -1.350 ns (~214 MHz) | -1.101 ns (~226 MHz) | +0.249 ns |

The 250 MHz lines are the headline: V80 ES now closes 250 MHz on
BOTH 512 KB and 1 MB caches. Pre-CD=1, V80 was effectively a
200 MHz part on these sizes.

## Production-silicon projection (`CLOCK_UNCERTAINTY_NS=0.035`)

V80 ES `-S` reports `clock_uncertainty = 0.300 ns`; production
UltraScale+ HBM (U250 / U55C) is `~0.035 ns`. The V80 deployment
TCL accepts an `CLOCK_UNCERTAINTY_NS` env var that overrides the
silicon's reported value at PnR time, so a build can model "what
will production silicon do".

| Cache | Knobs | ES (default uncertainty) | Production projection (`CLOCK_UNCERTAINTY_NS=0.035`) |
|---|---|---:|---:|
| 512 KB | CD=1, tuned | +0.012 ns (~250 MHz) | +0.030 ns (~252 MHz) |
| 2 MB   | CD=1, tuned | -0.380 ns (~228 MHz) | -0.345 ns (~230 MHz) |

The 2 MB delta is only +2 MHz — production silicon will NOT close
250 MHz on 2 MB caches. The 66-URAM cascade is structurally bound
(documented in the diminishing-returns table above). Closing 2 MB
at 250 MHz requires banked-SDP databank (see
[`doc/DESIGN_BANKED_SDP_DATABANK.md`](../DESIGN_BANKED_SDP_DATABANK.md))
or other architectural change.

```bash
PERIOD_NS=4.0 DB_LATENCY=3 SDP_WRITE_INPUT_REG=1 \
  PLACE_DIRECTIVE=ExtraNetDelay_high \
  PHYS_DIRECTIVE=AggressiveExplore \
  ROUTE_DIRECTIVE=AggressiveExplore \
  PNR=1 ./syn/vivado/v80_synth.sh
```

## Reproduce

```bash
cd syn/vivado

# 512 KB at 200 MHz on ES silicon (default, MET)
PERIOD_NS=5.0 PNR=1 ./v80_synth.sh

# 512 KB at 250 MHz with tuned knobs (post-route -0.090 ns)
PERIOD_NS=4.0 DB_LATENCY=3 SDP_WRITE_INPUT_REG=1 \
  PLACE_DIRECTIVE=ExtraNetDelay_high \
  PHYS_DIRECTIVE=AggressiveExplore \
  ROUTE_DIRECTIVE=AggressiveExplore \
  PNR=1 ./v80_synth.sh

# Experimental: 1 MB / 2 MB at 300 / 350 MHz (all miss; documented for
# planning purposes — see "experimental" table above)
SIZE=2M PERIOD_NS=3.333 DB_LATENCY=3 SDP_WRITE_INPUT_REG=1 \
  PLACE_DIRECTIVE=ExtraNetDelay_high \
  PHYS_DIRECTIVE=AggressiveExplore \
  ROUTE_DIRECTIVE=AggressiveExplore \
  PNR=1 ./v80_synth.sh
```

## Caveats

- ES silicon limits achievable frequency by ~50 MHz vs the design's
  structural ceiling. Production silicon should restore the gap.
- The 66-URAM cascade at 2 MB is a structural binding path on every
  board (not ES-specific) — 300+ MHz on 2 MB is not feasible without
  FSM-level pipelining.
- Versal NoC integration adds delay to system-level paths; OOC numbers
  are a lower bound for in-system timing.
